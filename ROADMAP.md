## Фаза 4 — Биллинг и баланс

**Решения (зафиксированы при входе в фазу):**
- **Единица:** 1 кредит = 1 генерация (независимо от модели генерации). Никаких дробных единиц — леджер держит целые кредиты, что оставляет модель гибкой под будущие не-генерационные сценарии.
- **Trial:** новому юзеру начисляется **1 бесплатный кредит** при регистрации (главный хук — показать вау-результат до оплаты). Гостевая сессия (`POST /auth/guest`) кредитов **не получает** — иначе бесплатный тир абьюзится одним запросом.
- **Паки** (разовые пополнения, gross / incl. VAT): Starter 5 → €4.99 · Popular 20 → €14.99 · Value 50 → €29.99. Минимум ~€5 — ниже фикс-комиссия Stripe (€0.25–0.30) регрессивно съедает экономику мелких платежей.
- **Без подписок** на этом этапе — только разовые пополнения по мере необходимости.
- **Экономика:** COGS ≈ 2 вызова image-модели на генерацию; на Nano Banana 2 (1K) ≈ €0.12/ген → валовая маржа ~80% даже на самом дешёвом паке. Выбор модели — по качеству, не по цене.

**Срезы (по одному PR на срез):**

- [x] **Срез 1 — `billing`-домен (кредиты + леджер, без Stripe):** сущности `credit_balances` (материализованный баланс, `user_id` unique) + `credit_transactions` (леджер: `type` enum `SignupBonus|Purchase|GenerationDebit|GenerationRefund`, `amount ±`, `reason`, nullable `generation_id`, nullable unique `stripe_event_id` для идемпотентности). Атомарное списание через условный `UPDATE ... WHERE balance >= :n` (проверка affected rows) в транзакции с записью леджера. API `GET /billing/balance`, `GET /billing/transactions`. `grantSignupBonus` при регистрации. Публичные методы `debit/refund/credit` для других модулей. Контракты `_contracts/billing/`.
- [x] **Срез 2 — гейтинг генерации по балансу:** `GenerationService.start()` дебетует 1 кредит **до** создания job (атомарный дебет исключает уход баланса в минус и «фантомный» pending-job); нет баланса → **HTTP 402** (`InsufficientCreditsException`). Рефанд кредита при провале в `run()` и при несоздании job-строки после дебета. Дебет-строка леджера без `generationId` (id ещё нет к моменту списания; в DTO он и не отдаётся) — рефанд ссылается на генерацию. e2e: 402 после исчерпания trial-кредита + рефанд→успешный ретрай.
- [ ] **Срез 3 — Stripe (пополнения):** ⏸ *отложен до заведения Stripe-аккаунта (после локального тестирования сервиса).* Checkout Session (`mode: payment`, `automatic_tax`), вебхук `checkout.session.completed` с идемпотентностью по `stripe_event_id` → начисление кредитов. Паки как константы с Stripe Price ID из конфига. Docs по Stripe SDK — через context7.
- [x] **Срез 4 — фронт (Nuxt):** `useBilling` (реальный `/billing/balance` + `/transactions`), экран пополнения `balance.vue` на данных API — пакеты Фазы 4 (5/€4,99 · 20/€14,99 · 50/€29,99), баланс, история транзакций; перехват **402** в `useGeneration` (`InsufficientCreditsError`) → `result.vue` ведёт на `/balance?reason=out-of-credits`; индикатор баланса в `gallery.vue` на реальных данных. Цены синхронизированы в `PRODUCT.md §4.2` / `DESIGN.md §7`. Кнопка оплаты — заглушка «Оплата скоро» (реальный Stripe-checkout → Срез 3).

## Фаза 4.5 — Аккаунты (регистрация, подтверждение email, линковка гостя)

Цель: закрыть дыру, из-за которой веб-флоу не проходится до конца. Кредиты гостям не выдаются (иначе бесплатный тир абьюзится одним запросом), а экрана регистрации на вебе нет — значит любая генерация из браузера упирается в 402. Фаза идёт **до** Telegram/i18n: без неё нельзя дать продукт живым людям.

**Решения (зафиксированы при входе в фазу):**
- **Passwordless:** email + 6-значный код из письма, без пароля. Код одновременно подтверждает адрес — отдельного этапа «верификация email» не появляется. Подробное обоснование — `PRODUCT.md` §4.3.
- **Момент гейта:** регистрацию просим на кнопке «Сгенерировать», не раньше. Гейт обязан быть до вызова модели (~€0,12 COGS за генерацию), и там же пик мотивации.
- **Линковка:** верификация кода с гостевым JWT **дозаполняет текущего** `User` (тот же `user.id`, фото/примерки/баланс сохраняются), а не создаёт нового.
- **Пароль не выпиливаем:** `POST /auth/register` / `POST /auth/login` остаются для e2e и будущей админки; веб-флоу идёт мимо них.

**Срезы (по одному PR на срез):**

- [x] **Срез 1 — `mail`-модуль:** `@Global`-модуль `api/src/mail` по паттерну `image-model` — абстрактный `BaseTransport` (+ `BaseTransportCtor.itIsMe`), реализации `SmtpTransport` (nodemailer, пул) и `LogTransport` (пишет письмо в лог), фабрика `createTransport` по `MAIL_PROVIDER`, `MailService` на абстракции. Локально — **Mailpit** в `docker-compose` (SMTP `:1025`, UI `:8025`), в тестах/CI — `log`. Шаблоны Handlebars в `mail/templates/` (html + text, `.hbs` копируются в `dist` через `assets`), первое письмо — код подтверждения. Проверено вживую: письмо доставлено в Mailpit (`npm run mail:test -- you@example.com`). **Прод-провайдер не выбран** (Mailgun EU / Postmark / Resend) — переключается одним env, но требует домена отправки с SPF/DKIM; вендорный HTTP API при необходимости добавляется новым транспортом.
- [x] **Срез 2 — passwordless OTP на бэке:** сущность `email_otp_codes` (bcrypt-хеш кода, `expires_at`, `attempts`, `consumed_at`, `request_ip`) + миграция, `POST /auth/otp/request` (200) и `POST /auth/otp/verify` (200). Код 6 цифр из `crypto.randomInt`, TTL 10 мин, 5 попыток, ресенд не чаще раза в минуту на адрес и 20 запросов в час с IP (429 с `retryAfterSeconds`); при выдаче нового кода прежние гасятся, повторное использование кода — 401. Все неуспехи верификации отдают одинаковый 401, а `request` — одинаковый ответ для известного и неизвестного адреса (не превращаем эндпоинт в проверку «зарегистрирован ли email»). Линковка через `OptionalJwtAuthGuard`: с гостевым токеном учётка дозаполняется (тот же `user.id`, trial начисляется), без токена — заводится новая; email занят → вход в существующий аккаунт с переносом фото/анализов/генераций гостя (`UsersRepository.mergeGuestInto`, одна транзакция) и удалением гостевой строки. Контракты `_contracts/auth/`, 14 e2e. Проверено вживую на Mailpit: гость (баланс 0) → код письмом → verify → тот же `user.id` с балансом 1.
- [x] **Срез 3 — веб:** модалка регистрации (`AuthModal`) на кнопке «Сгенерировать» — гейт открывается только гостю, выбор образа переживает модалку, после подтверждения кода сразу уходим на `/result`. Два шага в одной модалке: email → 6 цифр (авто-отправка по заполнению, `autocomplete="one-time-code"`), обратный отсчёт до повторной отправки из `resendAfterSeconds`, «Другой адрес», Esc/клик по фону/блокировка скролла. `useAuth` расширен: `user`/`isRegistered`, `ensureUser` (кто мы — по токену, гостя не заводит), `requestOtp`/`verifyOtp` с типизированными `OtpRateLimitError`/`InvalidOtpError`; 429 разбирается по `retryAfterSeconds` — до минуты это лимит на адрес (ведём на ввод кода, письмо уже ушло), больше — часовой лимит по IP (остаёмся на email). Состояние «залогинен» — email в галерее и на экране баланса, гостю там же честный текст про гостевую сессию. Проверено вживую (Mailpit + Playwright): гость с балансом 0 → код письмом → тот же `user.id` с балансом 1 и `signup_bonus`; неверный код не рвёт линковку; занятый адрес уводит в существующий аккаунт.

**Выход:** пользователь из браузера доходит до сгенерированного фото — регистрируется одним email и кодом, история гостя не теряется.

## Фаза 5 — i18n + Telegram Mini App

Цель: продукт говорит на языках плацдарма (RU/ES/DE) и живёт внутри Telegram — основного канала дистрибуции.

**Порядок внутри фазы: i18n идёт первым.** Он ничем не заблокирован и проверяется локально, тогда как Mini App нельзя ни открыть, ни проверить без публичного HTTPS — Telegram грузит его во встроенный webview. Тексты бота при этом сразу пишутся через уже готовые словари, а не переносятся в них потом.

**Решения (зафиксированы при входе в фазу):**
- **Стек i18n:** `@nuxtjs/i18n` (Vue I18n под капотом) с lazy-загрузкой словарей. Ручной composable дешевле на старте, но не даёт локализованных роутов и SEO-тегов, а DACH — стратегическая цель, а не побочный рынок.
- **URL:** `strategy: "prefix_except_default"`, `defaultLocale: ru` — `/` остаётся русским, немецкий и испанский живут на `/de/…` и `/es/…`. Индексируемые адреса на язык нужны для органики в DACH; внутри Mini App префикс не мешает.
- **Определение языка (по убыванию приоритета):** явный выбор пользователя (cookie + `User.locale` у залогиненных) → `language_code` из Telegram `initData` в Mini App → `Accept-Language` браузера → RU. `detectBrowserLanguage` с `useCookie: true`, `redirectOn: "root"`.
- **Локаль как свойство учётки:** `User.locale` (enum `Locale` = ru/es/de уже есть) — источник правды для писем и уведомлений бота, то есть для всего, что уходит пользователю, когда его вкладки нет. Смена языка в UI пишется в учётку; для этого появляется первый эндпоинт обновления профиля (`users`-контроллера сейчас нет вовсе).
- **Ошибки API не локализуем.** Бэкенд отдаёт код и статус, текст подбирает фронт из словарей. Иначе локаль придётся протаскивать в каждый ответ и держать словари в двух местах.
- **Каталог:** `name`/`description` уже `LocalizedText` в jsonb и отдаются целиком — язык выбирает фронт. А вот `groupName` — плоская русская строка, по которой к тому же фильтруются чипы; он становится enum в `_contracts` (правило контролируемых словарей), подписи уезжают в словари UI. В сиде сейчас `ru` + `en`, при том что поддерживаемые локали — ru/es/de: переводы 30 карточек на es/de — контентная работа, отдельный срез.

**Срезы (по одному PR на срез):**

- [x] **Срез 1 — i18n-каркас на вебе:** `@nuxtjs/i18n` (`prefix_except_default`, cookie `hairo-locale`, определение по правилу выше), словари `i18n/locales/{ru,de,es}.json`, все UI-строки вынесены из шаблонов, подписи таксономии (форма лица/длина/текстура/густота/повод) — тоже из словарей вместо const-мапов. Переключатель языка в хедере вместо статичного чипа «RU»; выбор пишется и в cookie, и в учётку через новый `PATCH /users/me` (контроллера `users` до этого не было вовсе).
