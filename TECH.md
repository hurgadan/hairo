## Хранение фото — S3-совместимое хранилище (зафиксировано)

Единый протокол (S3 API) на всех окружениях, переключение — только через env, без изменения кода. Абстракция в бэкенде: `StorageModule` (global) + `StorageService` на `@aws-sdk/client-s3` (`api/src/storage`).

- **Локальная разработка:** **MinIO** в `docker-compose` (`db:up`), S3 API на `:9000`, консоль на `:9001`. Бакет создаётся автоматически при старте (`onModuleInit`, только при `STORAGE_FORCE_PATH_STYLE=true`).
- **Продакшн:** **Cloudflare R2** (бакет с `jurisdiction: eu` — data residency под GDPR/биометрию; бесплатный egress; free tier покрывает старт; встроенный CDN). `region=auto`, `FORCE_PATH_STYLE=false`, endpoint `https://<account>.eu.r2.cloudflarestorage.com`, `STORAGE_PUBLIC_URL` = CDN-домен бакета.
- **Альтернатива для прода:** Hetzner Object Storage (Германия/ЕС, €4.99/мес) — если хочется один поставщик/DPA с VPS; минус — платный egress при росте.
- **Отдача:** публичный CDN-URL через `STORAGE_PUBLIC_URL`; если не задан — presigned URL (приватные объекты). Клиентская загрузка — через presigned PUT (browser → хранилище напрямую).
- **Env:** `STORAGE_ENDPOINT`, `STORAGE_REGION`, `STORAGE_ACCESS_KEY_ID`, `STORAGE_SECRET_ACCESS_KEY`, `STORAGE_BUCKET`, `STORAGE_FORCE_PATH_STYLE`, `STORAGE_PUBLIC_URL` (см. `.env.dist`).

## Отправка почты — SMTP-релей (зафиксировано)

Инфраструктурный модуль `mail` (`api/src/mail`, `@Global`) по тому же паттерну, что `image-model`/`llm-model`: абстрактный `BaseTransport` + реализации + фабрика `createTransport` по env + `MailService`, который работает с абстракцией и не знает провайдера.

- **Транспорты:** `smtp` (nodemailer, пул соединений) и `log` (печатает письмо в лог, ничего не отправляет).
- **Локальная разработка:** **Mailpit** в `docker-compose` (`db:up`) — SMTP на `:1025`, веб-интерфейс на `:8025`. Аутентификация не нужна: если `MAIL_SMTP_USER`/`PASSWORD` пусты, `auth` не передаётся вовсе. (Mailpit — поддерживаемая замена архивированного MailHog, порты и UX те же; чтобы вернуться на MailHog, достаточно поменять `image` в compose.)
- **Тесты/CI:** `MAIL_PROVIDER=log` — e2e не поднимают SMTP-сервер.
- **Продакшн:** SMTP-креды провайдера с EU-регионом (Mailgun EU / Postmark / Resend) — код не меняется, только env. Провайдер не выбран: решается при заведении домена отправки. Вендорный HTTP API (если понадобится — вебхуки доставки, шаблоны на стороне провайдера) добавляется новым классом с `itIsMe` и одной строкой в списке фабрики.
- **Шаблоны:** Handlebars в `mail/templates/{locale}/` — по два файла на письмо (`*.html.hbs` + `*.text.hbs`), все локали компилируются один раз на старте. `.hbs` копируются в `dist` через `assets` в `nest-cli.json`. Язык письма приходит от вызывающего (`ISendVerificationCode.locale`); если файла для него нет — берётся русский, поэтому новый язык в `Locale` не роняет старт, пока письма для него не написаны. Тема письма — единственный текст вне шаблона, живёт словарём в `mail/constants`.
- **Env:** `MAIL_PROVIDER`, `MAIL_FROM`, `MAIL_SMTP_HOST`, `MAIL_SMTP_PORT`, `MAIL_SMTP_SECURE`, `MAIL_SMTP_USER`, `MAIL_SMTP_PASSWORD` (см. `.env.dist`). Все необязательные — без них поднимается `log`-транспорт.
- **Проверка вживую:** `npm run mail:test -- you@example.com`.

## Интеграция с AI-моделями (зафиксировано)

Два независимых инфраструктурных модуля (`api/src/{module}`), у каждого свой клиент SDK — общий инстанс не шарим:

- **`image-model`** — генерация/рестайлинг изображений. Провайдер — Google AI (`@google/genai`), модель — Nano Banana / Gemini 2.5 Flash Image. Абстракция `BaseModel` + `createModel`/`itIsMe` — на будущее переключение между версиями модели через env (`IMAGE_MODEL`).
- **`llm-model`** — структурированный vision-анализ фото (форма лица, длина/текстура/густота волос и т.п. → JSON по схеме). MVP — только Gemini (`generateContent` + `responseSchema`), тот же паттерн абстракции, что и в `image-model`. LLM как класс задач — не только Gemini: большинство провайдеров (кроме Anthropic) совместимы с OpenAI-протоколом, что в будущем упростит переключение провайдера через env. На этапе MVP лишние интеграции не тащим — только Gemini.

Доменные модули (например `face-analysis`) обращаются к `llm-model`/`image-model` через DI, не работают с SDK напрямую — так же как `photos` не работает с `@aws-sdk/client-s3` напрямую, а идёт через `StorageService`.

## Data residency AI-обработки — открытый вопрос (вернуться перед запуском)

**Хранение** фото решено (R2, `jurisdiction: eu`), а **обработка** — нет. `image-model`/`llm-model` ходят в **Gemini Developer API** (`@google/genai` + API-ключ), а он **не даёт региональной привязки** — Google прямо не рекомендует его там, где нужна EU-only обработка персональных данных. Обучения на наших фото при этом нет (в ЕЭЗ/CH/UK Google применяет Paid Services terms даже к бесплатной квоте — это и написано в `/privacy`), но это про *использование* данных, а не про то, *где* они обрабатываются. То есть самый чувствительный поток проекта — фото лиц — сейчас единственное место, где EU-принцип не выдержан.

Альтернатива — **Vertex AI**: не другая модель, а вторая дверь к тем же Gemini. Отличия: вход по service account (проект Google Cloud) вместо API-ключа, регион пиннится (`europe-west4`, `europe-west3`, multi-region `eu`), Cloud DPA и опции zero-retention, биллинг через Google Cloud. SDK **тот же**, меняется только конструктор клиента внутри `GeminiModel`:

```ts
new GoogleGenAI({ apiKey });                                            // сейчас
new GoogleGenAI({ vertexai: true, project, location: "europe-west4" }); // Vertex
```

Абстракция `BaseModel`/`itIsMe`/`createModel` переезд переживает без изменений — правка локальна.

**Почему не делаем сейчас, но нельзя забыть:**

- **Конфликт «качество против residency».** `gemini-2.5-flash-image` (текущая) в EU-регионах Vertex развёрнута, а новые Nano Banana (`gemini-3-pro-image`, `gemini-3.1-flash-image` — в enum `ImageModel` как путь апгрейда) на середину 2026 доступны только через global endpoint. Принцип «модель выбираем по качеству, не по цене» (`ROADMAP.md`, Фаза 4) может упереться в EU-residency — это решение с двумя дорогими вариантами, и принимать его нужно осознанно, а не молча.
- **Пока нет живых пользователей — нет и персональных данных под риском.** Починить до запуска дёшево; после — это уже инцидент и правка политики задним числом.
- **Ловушка:** в Vertex-режиме с API-ключом SDK игнорирует заданную локацию и уходит на global endpoint — residency ломается молча, без ошибки. Проверять фактом запроса, а не конфигом.

**Триггеры вернуться:** перед публичным запуском (Фаза 7) · при смене `IMAGE_MODEL` на 3.x · если Google откроет EU-регион для Nano Banana.

**Что проверить в момент решения:** доступность нужной модели в `europe-west4`/`eu` (меняется быстро — смотреть консоль GCP, не статьи), цены Vertex против AI Studio, квоты, объём работы на service account в проде.

## Асинхронные шаги (анализ фото, генерация) — паттерн (зафиксировано)

Для MVP — без очереди/Redis. Контроллер создаёт запись задания со статусом `pending`, кидает fire-and-forget async-вызов (обязательно с `.catch()` — иначе unhandled rejection может уронить процесс, и статус останется зависшим), отвечает `202 Accepted`. Фронт поллит `GET /{module}/:id` до `completed`/`failed`.

Первое применение — `face-analysis` (см. `ROADMAP.md` Фаза 3). Статус-модель задания спроектирована на переиспользование в `generation` (Фаза 2/3), когда там появится реальная очередь (BullMQ/Redis) — заменится только механизм старта задания, API для фронта (create + poll) не изменится.

## ⚠️ Юридически-технический флаг (важно, не забыть)

- [ ] **Фото лиц = персональные данные.** Уточнение: фотография сама по себе **не** биометрия по GDPR (Recital 51) — ею она становится при обработке *для уникальной идентификации* человека, чего Hairo не делает (определение формы лица и текстуры волос ≠ идентификация). Режим ст. 9 и обязательный DSB по этому основанию, скорее всего, не включаются; осторожность в документах всё равно оправдана, но требования мягче, чем звучало в исходной формулировке этого пункта. Проверить с юристом до запуска.
  - ✅ Явное согласие на обработку, прозрачная политика (`/privacy`).
  - ✅ Сроки хранения, право на удаление, минимизация (`retention`-модуль, 30 дней неактивности).
  - ✅ Где хостится хранилище — R2, `jurisdiction: eu`.
  - ✅ Условия Google AI по обучению на загруженных данных: в ЕЭЗ/CH/UK обучения нет даже на бесплатной квоте.
  - [ ] **Где происходит обработка** — не закрыто, см. раздел про data residency выше.
- [ ] **`/privacy` описывает не всё, что происходит.** §4 политики говорит про хранение в ЕС и про отсутствие обучения на фото, но молчит о том, что сама *обработка* уходит за пределы ЕЭЗ и по какому механизму. Ст. 13(1)(f) GDPR требует прямо сообщать о передаче в третью страну и называть основание (adequacy / SCC). Закрывается вместе с решением по Vertex: либо обработка переезжает в EU и абзац становится правдой целиком, либо в политике появляется явный абзац про трансфер. Полный список того, что политика не закрывает, — `PROJECT.md` §4.12.
